إزاي تفكري كـ Backend Developer شاطرة قبل ما تكتبي الكود

الفرق الحقيقي مش إنك تحفظي إن routes في فولدر وcontrollers في فولدر. الفرق إنك تبقي فاهمة: الكود ده مسؤوليته إيه؟ يتحط فين؟ مين المفروض يعرف عنه؟ لو المشروع كبر، هل هعرف أغيره من غير ما أكسر 20 حاجة؟ لو حصل Bug، هعرف أوصل له بسرعة؟ وده التفكير اللي هنمشي بيه في كل نقطة في الصفحة دي.

1) أول قاعدة: متبدأيش بالكود

لما ييجي Requirement زي "عايزين Endpoint يعمل Create Order":

❌ الغلط

إنك تفتحي VS Code على طول وتكتبي:

example — غلط
app.post('/orders', async (req, res) => {
  // 150 سطر
});
🔵 الصحيح

إنك الأول تسألي نفسك سلسلة أسئلة قبل ما تلمسي الكود خالص:

الـRequest جاية منين؟ ↓ مين يتأكد إن المستخدم مسجل؟ ↓ مين يتأكد إن Body صح؟ ↓ مين ينفذ Business Logic؟ ↓ مين يتعامل مع Database؟ ↓ مين يرجع HTTP Response؟ ↓ لو حصل Error، مين يمسكه؟ ↓ إزاي هعرف بعدين حصل إيه؟
⚡ القاعدة

لو قدرتِ تجاوبي الأسئلة دي قبل الكود، نص شغلك خلص.

2) الـMental Model الأساسية لأي Backend

أي Feature تقريبًا تقدري تشوفيها بالشكل ده — وده أهم Flow في الموضوع كله:

Client ↓ Request ↓ Route ↓ Middleware ↓ Validation ↓ Controller ↓ Service ↓ Model / Repository ↓ Database ↓ Service ↓ Controller ↓ Response
🟪 لاحظي

خلينا في باقي فصول الصفحة دي نفهم كل طبقة "ليه موجودة" بدل "بنكتب فيها إيه" — وده بالظبط اللي هيفرق بينك وبين حد بيحفظ Folder Structure بس.

📗 Chapter 2

Project Structure & Code Organization

هنا هنفهم ليه بنفصل الكود لطبقات، وكل طبقة مسؤوليتها إيه بالظبط، عشان المشروع يفضل قابل للتوسع من غير ما يتحول لكتلة واحدة محدش فاهمها.

1) المشكلة اللي بنحلها

تخيلي كل الكود في File واحدة:

example
app.post('/register', ...)
app.post('/login', ...)
app.get('/users', ...)
app.delete('/users/:id', ...)
app.post('/orders', ...)
app.get('/products', ...)

وتحت كل Route: validation، database، password hashing، email sending، business logic، error handling، response. بعد فترة هتلاقي app.js = 5000 سطر.

🟠 المشكلة الحقيقية

المشكلة مش بس إن الملف كبير. المشكلة الحقيقية: كل حاجة عارفة كل حاجة. وده بيخلي التعديل خطر.

🧠 فكري في المشروع كشركة

مش منطقي موظف الاستقبال: يستقبل العميل + يعمل الحسابات + يمضي العقد + يدير المخزن + يصلح الكمبيوتر. كل واحد له مسؤولية. نفس الفكرة بالظبط في الكود.

2) Folder Structure

ممكن مشروع يبقى:

example
src/
│
├── routes/
├── controllers/
├── services/
├── models/
├── middlewares/
├── validators/
├── utils/
├── config/
├── app.js
└── server.js
⚠️ خلي بالك

الـ Folder Structure مش هدف. يعني مش النجاح إن عندك 15 Folder. النجاح إن كل Folder لها Responsibility واضحة.

3) Routes

الـ Route دورها بسيط جدًا: لما Request بشكل معين تيجي، روح شغل مين؟

example
router.post(
  '/users',
  validateCreateUser,
  createUser
);
POST /users ↓ validateCreateUser ↓ createUser
❌ مينفعش

تحطي جوه Route كل الـ validate/bcrypt/database/send email/business rules/response مباشرة. ليه؟ لأن Route مسؤوليتها Routing، مش Business Logic.

4) Controller

فكري في Controller كأنها المترجم بين HTTP والـ Application. هي تعرف حاجات زي req، res، status code، query، params، body.

example
async function createUser(req, res, next) {
  try {
    const user = await userService.createUser(
      req.body
    );

    res.status(201).json({
      data: user
    });
  } catch (error) {
    next(error);
  }
}

خدي بالك Controller دي صغيرة. ليه؟ لأنها قالت: هات الـ Body ← ابعتها Service ← خد النتيجة ← حولها HTTP Response. وخلاص.

5) Service

Service دي قلب الـ Business Logic. يعني لو Requirement بيقول "مينفعش User بنفس Email يتسجل مرتين" — دي Business Rule، مكانها الطبيعي Service.

example
async function createUser(data) {
  const existingUser =
    await User.findOne({
      email: data.email
    });

  if (existingUser) {
    throw new AppError(
      'Email already exists',
      409
    );
  }

  const hashedPassword =
    await bcrypt.hash(
      data.password,
      12
    );

  const user =
    await User.create({
      ...data,
      password: hashedPassword
    });

  return user;
}

لاحظي Service مش محتاجة تعرف req، res، HTTP، ولا Express. دي نقطة مهمة جدًا.

🔹 ليه فصل Business Logic عن HTTP مهم؟

تخيلي بعدين عندك نفس Logic تتنفذ من HTTP API، Cron Job، Queue Worker، CLI Script، أو WebSocket Event. لو الـ Business Logic مربوطة بـ req/res، هتضطري تعيدي الكود. لكن لو عندك userService.createUser()، أي مكان يقدر يستخدمها.

6) Model

Model مسؤولة عن شكل البيانات والتعامل مع Database. مثلًا Mongoose:

example
const userSchema =
  new mongoose.Schema({
    name: String,
    email: String,
    password: String
  });

الـ Model تعرف شكل User، أنواع الحقول، Indexes، Database operations. لكن مش من الأفضل تحطي فيها كل Business Logic بتاعت المشروع بدون سبب.

7) Middleware

فكري في Middleware كأنها حاجات بتحصل على Request قبل ما توصل للهدف النهائي:

Request ↓ Authentication ↓ Authorization ↓ Validation ↓ Controller
example
router.delete(
  '/users/:id',
  authenticate,
  requireAdmin,
  deleteUser
);

دي جميلة جدًا لأنها بتقري كأنها جملة: Delete user، بس الأول اتأكد إنه authenticated وبعدين admin وبعدين نفذ deleteUser.

8) Validators

الـ Validator تسأل: الداتا اللي دخلتلي صالحة أصلًا ولا لأ؟ (email موجود؟ email format صح؟ password 8 characters؟ age number؟)

🟪 فرق مهم

Validation: هل شكل الداتا صح؟ Business Rule: هل العملية مسموح تحصل؟ مثلًا: "Email valid format؟" ← Validation. "Email already exists؟" ← Business Logic / Service. دي من أهم الفروقات اللي تخلي الكود منظم.

9) Utils / Helpers

دي حاجات عامة صغيرة ملهاش Business Meaning كبير، زي generateRandomCode()، formatDate()، slugify()، calculatePagination().

⚠️ خلي بالك من كارثة اسمها utils.js

يعني متحطيش فيها 300 Function ملهمش علاقة ببعض. الأفضل تقسيمها حسب الحاجة:

example
utils/
├── date.js
├── pagination.js
└── string.js

10) Config

أي Settings تخص تشغيل الـ Application: Database URL، Port، JWT configuration، CORS settings، Mail configuration. بدل ما كل File يعمل process.env.JWT_SECRET بنفسه، ممكن تعملي Config Layer:

example
const config = {
  port: Number(process.env.PORT) || 3000,
  jwtSecret: process.env.JWT_SECRET,
  databaseUrl: process.env.DATABASE_URL
};

وبعدين باقي المشروع يستخدم config.jwtSecret. ده بيديكي مكان واحد لكل Configuration.

11) فصل app.js عن server.js

دي حركة صغيرة لكن مهمة.

🔹 app.js — يجهز Express Application

example
const express = require('express');

const app = express();

app.use(express.json());

app.use('/api/users', userRoutes);

app.use(errorHandler);

module.exports = app;

🔹 server.js — مسؤول عن تشغيل السيرفر

example
const app = require('./app');

const server =
  app.listen(3000, () => {
    console.log('Server started');
  });

ليه الفصل؟ لأن app.js = Application configuration وserver.js = Runtime / process startup. وده مفيد جدًا في Testing، لأن Test تقدر تستورد app من غير ما تفتح Port حقيقي.

12) إزاي أعرف الحاجة تتحط فين؟

اسألي السؤال ده: "الكود ده بيتكلم مع مين؟"

لو بيتعامل مع...مكانه
req / resController
هل ينفع العملية تحصل؟ إزاي تحصل؟Service
DatabaseModel / Repository
Request تكمل ولا تتوقف؟Middleware
شكل الـ InputValidator
Function عامة ملهاش Business MeaningUtility
⚡ الخلاصة

دي طريقة تفكير أهم من حفظ Folder Structure.

🆚 Don't Confuse These

الأولالتانيالفرق ببساطة
ValidationBusiness Ruleالأولى بتتأكد إن شكل الداتا صح (Email format مثلًا). التانية بتتأكد إن العملية مسموح تحصل فعليًا (زي عدم تكرار Email).
ControllerServiceالأولى بترجم بين HTTP والتطبيق (req/res بس). التانية فيها الـ Business Logic الحقيقي، من غير ما تعرف حاجة عن HTTP.
app.jsserver.jsالأول بيجهز الـ Express Application نفسها. التاني مسؤول بس عن تشغيلها كـ Process حقيقي على Port.

❌ Common Mistakes

  • كتابة كل حاجة (validation + database + business logic + response) جوه الـ Route مباشرة — بيخلي التعديل والاختبار صعب جدًا مع الوقت.
  • حط كل Business Logic جوه الـ Controller — Controller المفروض تبقى Thin، الـ Logic الحقيقي مكانه Service.
  • الخلط بين Validation وBusiness Rule — بيؤدي لكود غير منظم، ولحاجات زي Validation checks بتتكرر جوه Service بدل ما تتحط في Validator من الأول.

🎤 Interview Questions

إيه الفرق بين Controller وService؟
بيسأل عن إيه؟فهمك لتقسيم المسؤوليات بين طبقة الـ HTTP وطبقة الـ Business Logic. نفكر إزاي؟فكري: لو حبيت تشغلي نفس الـ Logic من مكان تاني غير HTTP Request (زي Cron Job)، هل الكود الحالي يسمحلك بده من غير تعديل؟ الإجابة المختصرةController مسؤوليتها الترجمة بين HTTP والتطبيق: تاخد الـ Request، تنادي الـ Service المناسبة، وتحول النتيجة لـ HTTP Response. Service فيها الـ Business Logic الفعلي، ومش بتعرف حاجة عن req أو res. بالتفصيللو الـ Business Logic اتكتبت جوه الـ Controller مباشرة، هتبقى مربوطة بـ Express تحديدًا، ومحتاجة تتكرر لو عايزة تستخدميها من مكان تاني (Queue Worker مثلًا). لما تفصليها في Service، أي مكان في المشروع يقدر ينادي نفس الـ Function. ممكن يسأل Follow-upهل الـ Service ينفع تنادي Service تانية؟ (أيوة، طبيعي جدًا إن Service تستخدم Services تانية لتنفيذ عملية مركبة).
ليه بنفصل app.js عن server.js؟
بيسأل عن إيه؟فهمك لفايدة فصل إعداد الـ Application عن تشغيلها الفعلي. نفكر إزاي؟فكري إزاي هتكتبي Test لـ Endpoint من غير ما تفتحي Port حقيقي على جهازك. الإجابة المختصرةapp.js بيجهز الـ Express Application (Middlewares وRoutes) ويصدرها. server.js بس بينادي app.listen() عشان يشغلها كـ Process حقيقي. بالتفصيلالفصل ده بيسمحلك في الـ Tests إنك تعملي require('./app') وتستخدميها مباشرة مع مكتبة زي Supertest، من غير ما يفتح فعليًا Port على الجهاز — وده بيخلي الـ Tests أسرع وأنضف. ممكن يسأل Follow-upلو المشروع بسيط جدًا، لازم أفصلهم؟ (مش إجباري في مشروع صغير جدًا، بس بيبقى عادة كويسة من البداية عشان لما المشروع يكبر ويحتاج Testing متضطريش تعيدي الهيكلة).

router.post(path, ...middlewares, controller)، module.exports = app، app.listen(port, callback).

أهم الأخطاء

  1. ليه مينفعش نحط الـ Business Logic كلها جوه الـ Route؟
  2. إيه الفرق بين Validation وBusiness Rule؟
  3. Service بتعرف حاجة عن req أو res؟ ليه؟
  4. ليه بنفصل app.js عن server.js؟
👁️ اعرضي الإجابات

1) لأن ده بيخلي الملف عملاق ومحدش يقدر يتأكد إن التعديل مش هيكسر حاجة تانية؛ كل طبقة لازم تبقى مسؤولة عن حاجة واحدة بس.

2) Validation بتتأكد من شكل الداتا (Email format مثلًا)، Business Rule بتتأكد إن العملية مسموح تحصل فعليًا (زي منع تكرار Email).

3) لأ، وده مقصود؛ عشان تقدري تستخدمي نفس الـ Business Logic من أي مكان (Cron Job، Queue، CLI) من غير ما تكون مربوطة بـ HTTP.

4) عشان نقدر نستورد app في الـ Tests من غير ما نفتح Port حقيقي، وعشان نفصل بين "تجهيز التطبيق" و"تشغيله كـ Process".

📗 Chapter 3

Environment & Configuration Management

إزاي نخلي الإعدادات الحساسة (Secrets) بعيدة عن الكود نفسه، وإزاي نخلي نفس المشروع يشتغل بشكل مختلف حسب البيئة (Development/Testing/Production) من غير ما نلمس الكود.

1) الفكرة

تخيلي كاتبة في الكود:

example — غلط
const dbUrl =
  'mongodb://username:password@...';
❌ ورفعتِ الكود GitHub

مبروك، الـ Password بقت Public. عشان كده عندنا Environment Variables.

2) .env و dotenv

.env
PORT=3000
DATABASE_URL=mongodb://...
JWT_SECRET=super-secret

وفي الكود:

example
process.env.DATABASE_URL

في مشاريع كتير بنستخدم dotenv:

example
require('dotenv').config();

وده يحمّل .env. الفكرة الأساسية:

.env ↓ Environment Variables ↓ process.env ↓ Application

3) أهم قاعدة

أي حاجة Secret أو Environment-specific أو Deployment-specific متتكتبش Hardcoded. مثلًا: Database URL، JWT Secret، API Key، SMTP password، Cloud credentials.

4) .env.example

دي مش فيها القيم الحقيقية:

.env.example
PORT=
DATABASE_URL=
JWT_SECRET=

ليه؟ عشان Developer جديد يعرف المشروع محتاج Variables إيه، لكن من غير Secrets.

5) Development / Testing / Production

نفس Application ممكن تشتغل في بيئات مختلفة:

Development → جهازك | Testing → Tests | Production → السيرفر الحقيقي

ممكن Database تبقى: Development → mongodb://localhost/dev-db، Testing → mongodb://localhost/test-db، Production → cloud-production-db. نفس الكود، لكن Config مختلفة.

🔹 NODE_ENV

example
if (
  process.env.NODE_ENV === 'production'
) {
  // production behavior
}

مثال: Development → stack trace تظهر. Production → stack trace متظهرش للـ Client.

6) طريقة التفكير في Configuration

⚡ اسألي

لو القيمة دي هتختلف لما أنقل المشروع من Laptop لسيرفر، هل المفروض تكون في الكود؟ غالبًا لأ.

❌ Common Mistakes

  • كتابة Secrets (Database URL، API Keys) مباشرة في الكود — بتتسرب فورًا لو الكود اترفع مكان عام زي GitHub.
  • رفع ملف .env الحقيقي على Git — المفروض .env يكون في .gitignore، وبس .env.example يترفع.
  • افتراض إن نفس Database/Config تصلح لكل البيئات — Development وTesting وProduction لازم يكون ليهم Config مستقلة.

🎤 Interview Questions

ليه بنستخدم Environment Variables بدل ما نكتب القيم مباشرة في الكود؟
بيسأل عن إيه؟فهمك لأمان الـ Secrets وفصل الإعدادات عن الكود. نفكر إزاي؟فكري: لو رفعتي الكود على GitHub بأي Secret مكتوب جواه، مين يقدر يشوفه؟ الإجابة المختصرةعشان الـ Secrets متفضلش مكشوفة في الكود نفسه (اللي غالبًا بيترفع على Git)، وعشان نقدر نغيّر القيم دي حسب البيئة (Development/Production) من غير ما نلمس الكود خالص. بالتفصيللو Database Password اتكتب Hardcoded ورُفع الكود على مستودع عام، أي حد يقدر يشوفه ويستخدمه. الـ Environment Variables بتتخزن في مكان منفصل (.env محليًا، أو Secrets Manager في الـ Production) وبتتقرأ وقت التشغيل بس. ممكن يسأل Follow-upلو نسيتِ تحطي .env في .gitignore وترفع بالغلط، إيه الحل؟ (لازم تغيّري كل الـ Secrets دي فورًا (Rotate)، لأن مجرد حذفها من الكود لاحقًا مش كافي؛ هي فعليًا اتسربت في الـ Git History).

📗 Chapter 4

Error Handling Strategy

هنا الفرق بين Junior بيحل Error لما تظهر، وDeveloper عامل System للـ Errors من الأول.

1) الغلط الشائع

example — غلط
try {
  ...
} catch (error) {
  console.log(error);
  res.status(500).send('error');
}

في كل Controller. ده Repetition.

2) فكري في Error كـFlow

Something fails ↓ Throw Error ↓ Error travels upward ↓ Global Error Handler ↓ Log ↓ Correct HTTP Response

3) Custom Error

example
class AppError extends Error {
  constructor(message, statusCode) {
    super(message);

    this.statusCode =
      statusCode;

    this.isOperational =
      true;
  }
}

وبعدين:

example
throw new AppError(
  'User not found',
  404
);

Service مش محتاجة تعمل Response. هي بس بتقول: حصلت مشكلة من النوع ده.

4) Operational Errors

دي Errors متوقعة أثناء تشغيل الـ Application، مثلًا: User not found، Invalid credentials، Email already exists، Forbidden، Validation failed. دي مش Bugs في الكود بالضرورة.

أما Cannot read properties of undefined دي غالبًا Programming Error. الفرق مهم.

5) Global Error Handler

example
app.use(
  (err, req, res, next) => {

6) 404

404 مش لازم معناها Error انفجرت. معناها: مفيش Route مطابقة. آخر Routes:

example

  next(
    new AppError(
      'Route not found',
      404

بعدها Global Error Handler.

هل متوقعة؟ ↓ هل Client سببها؟ ↓ هل Server سببها؟ ↓ Status المناسب إيه؟ ↓ إيه اللي Client محتاج يعرفه؟ ↓ إيه اللي Developer محتاج يعرفه؟ ↓ هل لازم تتعمل Log؟

Debugging

دي من أهم Skills في البرمجة كلها — إزاي توصلي لسبب المشكلة بسرعة، بدل ما تجربي تعديلات عشوائية.

1) المطور الضعيف مقابل الشاطر

❌ المطور الضعيف

لما Bug تحصل، يجرب تعديلات عشوائية.

🔵 المطور الشاطر

يكوّن Hypothesis ← يختبرها ← يضيّق نطاق المشكلة.

2) أهم قاعدة Debugging

متقوليش: "الكود مش شغال". قولي: "إيه بالضبط آخر نقطة أنا متأكدة إنها شغالة؟"

Frontend ↓ API ↓ Route ↓ Middleware ↓ Controller ↓ Service ↓ Database

مثال: لو Frontend بيقول 500. ابدئي: "هل Request وصلت Backend؟" آه. "Route matched؟" آه. "Authentication passed؟" آه. "Controller دخلت؟" آه. "Service رجعت؟" لأ. كده المشكلة ضاقت لـ Service.

3) Error Message

متقريش "Error Error Error" بس. ركزي في: Error Type، Message، File، Line، Stack Trace.

example
TypeError:
Cannot read properties of undefined
(reading 'email')

at createUser
userService.js:42

هو بيقولك تقريبًا: في userService.js line 42 فيه حاجة undefined وإنتِ بتحاولي تقري email منها. ده Clue مباشر.

4) Stack Trace

Stack Trace كأنها آثار خطوات:

Route ↓ Controller ↓ Service ↓ Function X ↓ Error

بتقولك: وصلنا للـ Error إزاي؟ متبصيش بس على أول Line أو آخر Line. اقري أول Frame من Code إنتِ كاتباه.

5) VS Code Debugger

بدل:

example — غلط
console.log('1');
console.log('2');
console.log(user);

اعملي Breakpoint. وقف الكود عند سطر معين. وشوفي req.body، user، token، result بالراحة.

Step Over

نفذ السطر الحالي وروح للبعده، من غير ما تدخل جوه Function.

Step Into

Function اتناديت؟ ادخل جواها وشوفها بتعمل إيه.

6) Debugging async/await

لو:

example
const user =
  await User.findById(id);

السؤال: id قيمتها إيه؟ Query اتنفذت؟ رجعت null؟ عملت throw؟ مش "Mongo بايظة".

7) طريقة Debugging فعالة: Expected مقابل Actual

اكتبي في دماغك:

Expected ↕ Actual
example
Expected:
req.user.id = "123"

Actual:
req.user = undefined

يبقى دوري قبل النقطة دي. مش بعدها.

❌ Common Mistakes

  • تجربة تعديلات عشوائية من غير Hypothesis واضحة — بتضيع وقت أكتر وممكن تخفي المشكلة الحقيقية.
  • الاعتماد على console.log فقط بدل الـ Debugger — بيبطئ عملية التشخيص خصوصًا في Flows معقدة أو async.
  • تجاهل قراءة الـ Stack Trace بالكامل — أول Frame من كود إنتِ كاتباه غالبًا بيوريكي مكان المشكلة الحقيقي.

🎤 Interview Questions

إزاي تقربي من مصدر Bug في Backend فيه أكتر من طبقة (Route/Middleware/Controller/Service/DB)؟
بيسأل عن إيه؟منهجيتك في تضييق نطاق المشكلة بدل التخمين العشوائي. نفكر إزاي؟فكري في الـ Request كأنه بيمشي في خط أنابيب من طبقة لطبقة؛ إنتِ محتاجة تعرفي عند أي نقطة بالظبط توقف السلوك الصحيح. الإجابة المختصرةبتتبعي الـ Request طبقة طبقة (Route → Middleware → Controller → Service → Database) وتتأكدي عند كل نقطة هل السلوك المتوقع حصل ولا لأ، لحد ما توصلي لآخر نقطة شغالة صح. بالتفصيلبدل "الكود مش شغال"، بتسألي: هل الـ Request وصل الـ Backend؟ هل الـ Route اتطابقت؟ هل الـ Middleware عدّت؟ هل دخلنا الـ Controller؟ هل الـ Service رجعت نتيجة؟ أول نقطة الإجابة فيها "لأ" هي مكان المشكلة. ممكن يسأل Follow-upلو المشكلة في Service بس مش واضح فين بالظبط، تعملي إيه؟ (تحطي Breakpoint جوه الـ Service نفسها وتتبعي قيم المتغيرات سطر سطر، أو تقارني Expected vs Actual عند كل خطوة).

📗 Chapter 9

Async Code Organization

ده من أهم الأجزاء جدًا. الفكرة مش بس تعرفي await. لازم تعرفي: إمتى العمليات تعتمد على بعض وإمتى لا.

1) Sequential

example
const user =
  await getUser();

const orders =
  await getOrders(user.id);

دي لازم Sequential. ليه؟ لأن getOrders محتاجة user.id:

getUser ↓ user.id ↓ getOrders

2) Parallel

لكن:

example — بطيء بدون داعي
const products =
  await getProducts();

const categories =
  await getCategories();

لو الاتنين ملهمش علاقة، إنتِ كده بتضيعي وقت. لو getProducts = 1 second وgetCategories = 1 second، Sequential: 1 + 1 ≈ 2 seconds. Parallel:

example
const [products, categories] =
  await Promise.all([
    getProducts(),
    getCategories()
  ]);

تقريبًا: max(1, 1) ≈ 1 second.

3) أهم سؤال قبل await

اسألي: هل السطر اللي بعده محتاج نتيجة السطر الحالي؟ لو آه → Sequential. لو لأ → فكري في Parallel. دي واحدة من أكتر الحاجات اللي تفرق في Performance.

4) تجنب Blocking Code

Node ممتازة في I/O. لكن لو عملتي:

example — غلط
for (
  let i = 0;
  i < 10_000_000_000;
  i++
) {}

JavaScript Thread هتتخنق:

Request A ↓ CPU-heavy loop ↓ Event Loop blocked ↓ B / C / D مستنيين

ففكري: هل العملية I/O ولا CPU intensive؟ دي قاعدة مهمة جدًا في Node.

5) Callback Hell

بدل:

example — غلط
a(() => {
  b(() => {
    c(() => {
      d(() => {});
    });
  });
});

استخدمي Promises وasync/await.

🆚 Don't Confuse These

الأولالتانيالفرق ببساطة
Sequential awaitPromise.all Parallelالأول لما كل عملية محتاجة نتيجة اللي قبلها. التاني لما العمليات مستقلة عن بعض، فتشغيلها مع بعض بيوفر وقت.

❌ Common Mistakes

  • تنفيذ عمليات مستقلة بـ await متتابع بدل Promise.all — بيزود وقت الاستجابة بدون داعي.
  • تنفيذ عملية CPU-heavy (Loop ضخم) في نفس الـ Thread الرئيسي — بيوقف الـ Event Loop ويأثر على كل الـ Requests التانية.

🎤 Interview Questions

بيسأل عن إيه؟فهمك للاعتمادية بين العمليات الـ Async وتأثيرها على الأداء. نفكر إزاي؟فكري: هل نتيجة العملية التانية محتاجة نتيجة الأولى أصلًا؟ الإجابة المختصرةلو العملية التانية محتاجة نتيجة الأولى، لازم Sequential (await واحدة ورا التانية). لو العمليتين مستقلتين تمامًا عن بعض، الأفضل Promise.all عشان تتنفذوا في نفس الوقت وتوفري وقت الاستجابة الكلي. بالتفصيلمثلًا getOrders(user.id) لازم تستني نتيجة getUser() الأول عشان تعرفي الـ id. لكن getProducts() وgetCategories() في صفحة عرض منتجات غالبًا مالهومش علاقة ببعض، فتشغيلهم بـ Promise.all بيخلي الوقت الكلي تقريبًا مساوي لأبطأهم بدل مجموعهم. ممكن يسأل Follow-upلو واحدة من العمليات في Promise.all فشلت، إيه اللي بيحصل؟ (Promise.all بترفض فورًا لو أي Promise فيها فشلت؛ لو عايزة تكملي حتى لو واحدة فشلت، تستخدمي Promise.allSettled بدلها).

Code Quality & Clean Code

هنا فيه قاعدة مهمة: Clean Code مش أقصر Code. Clean Code يعني Developer تاني يقدر يفهم نيتك بسرعة.

1) Single Responsibility

Function تعمل حاجة واحدة واضحة.

❌ سيئة
example — غلط
async function processUser() {
  // validate
  // create
  // send mail
  // create invoice
  // log
  // analytics
}
🔵 أفضل
example
createUser()
sendWelcomeEmail()
createInvoice()
trackRegistration()

مش لازم تبالغي في التقسيم، لكن كل Function يبقى ليها Purpose واضح.

2) Small Functions

مش معنى كده كل 3 أسطر Function. الفكرة: لما Function تبدأ تعمل أكتر من Concept، فكري تقسميها.

3) Naming

اسم سيئ:

example — غلط
const x = getData();

اسم أفضل:

example
const activeUsers =
  getActiveUsers();

اسم Function handle() غامض. لكن createOrder()، calculateOrderTotal()، validateCoupon() واضحة.

4) Magic Values

سيئ:

example — غلط
if (attempts >= 5) {
}

ليه 5؟ أفضل:

example
const MAX_LOGIN_ATTEMPTS = 5;

if (
  attempts >= MAX_LOGIN_ATTEMPTS
) {
}

دلوقتي المعنى واضح.

5) DRY (Don't Repeat Yourself)

بس الناس ساعات تبالغ. لو شوفتِ سطرين شبه بعض مرة أو مرتين، مش لازم فورًا تعملي Abstraction معقدة.

⚡ قاعدة حلوة

Duplication بسيطة أحيانًا أرحم من Abstraction غلط. اعملي Reuse لما يكون فيه Concept فعلي متكرر.

6) Controllers الضخمة

لو Controller فيها 200 lines، غالبًا فيها Business Logic مش مكانها. Controller الأفضل تكون Thin:

example
async function checkout(
  req,
  res,
  next
) {
  try {
    const result =
      await checkoutService.checkout({
        userId: req.user.id,
        items: req.body.items
      });

    res.status(201).json({
      data: result
    });
  } catch (error) {
    next(error);
  }
}

ده جميل.

❌ Common Mistakes

  • Function واحدة بتعمل حاجات كتير مش مرتبطة (validate + create + email + invoice) — صعب فهمها واختبارها وتعديلها.
  • استخدام أرقام أو نصوص Magic بدون تسمية (زي 5 أو 'admin') — بيصعب فهم المعنى وتعديل القيمة لاحقًا.
  • المبالغة في DRY وعمل Abstraction معقدة لمجرد سطرين متشابهين — أحيانًا التكرار البسيط أوضح من طبقة Abstraction غير ضرورية.

Testing مش معناها أتأكد إن Function بترجع 2 بس. الفكرة: أثبت إن Behavior المهم مش هيتكسر بعدين.

1) Unit Test

اختبري وحدة صغيرة. مثال: calculateTotal() — لو 100 + 50 يرجع 150.

2) Integration Test

اختبري أجزاء بتشتغل مع بعض:

POST /users ↓ Route ↓ Controller ↓ Service ↓ Database ↓ Response

example

⚠️ خلي بالك

Mock يعني: بدل Dependency حقيقية، استخدم نسخة Fake متحكم فيها. مثال: إنتِ بتختبري OrderService، بس مش عايزة تبعتي Email حقيقية. تعملي Mock لـ emailService.send().

📗 Chapter 15

Graceful Shutdown & Process Management

دي نقطة ناس كتير بتتجاهلها. تخيلي السيرفر شغال وعنده Requests شغالة وDatabase connection وOpen sockets، وبعتيله Shutdown.

1) الغلط الشائع

❌ اقفل فورًا

ممكن Request تكون في نص Payment.

2) Graceful Shutdown

الفكرة:

وصل SIGTERM ↓ بطل تستقبل Requests جديدة ↓ استنى Requests الحالية تخلص ↓ اقفل HTTP Server ↓ اقفل Database ↓ Exit

3) SIGINT مقابل SIGTERM

SIGINT: غالبًا لما تعملي Ctrl + C. SIGTERM: غالبًا Environment أو Process Manager يقول "اقفل".

4) مثال كود

example
const shutdown =
  async () => {
    console.log(
      'Shutting down...'
    );

    server.close(
      async () => {
        await mongoose
          .connection
          .close();

        process.exit(0);
      }
    );
  };

process.on(
  'SIGTERM',
  shutdown
);

process.on(
  'SIGINT',
  shutdown
);

❌ Common Mistakes

  • قفل السيرفر فجأة بدون انتظار الـ Requests الحالية — ممكن Request تكون في منتصف عملية حساسة زي Payment وتتقطع فجأة.
  • عدم إغلاق اتصال الـ Database بشكل صريح عند إيقاف السيرفر — ممكن يسبب Connections معلقة أو مشاكل عند إعادة التشغيل.

🎤 Interview Questions

إيه فايدة Graceful Shutdown، وليه مينفعش نقفل السيرفر فجأة؟
بيسأل عن إيه؟فهمك لأهمية إدارة دورة حياة الـ Process بشكل آمن، خصوصًا وقت الـ Deployment أو إعادة التشغيل. نفكر إزاي؟فكري في مستخدم في نص عملية Payment وقت ما السيرفر بيتقفل فجأة. الإجابة المختصرةGraceful Shutdown بيضمن إن السيرفر يبطل يستقبل Requests جديدة، لكن يستنى الـ Requests الحالية تخلص، ويقفل الاتصالات (زي Database) بشكل نظيف قبل ما الـ Process يقفل خالص، بدل ما يقطع كل حاجة فجأة. بالتفصيللو السيرفر اتقفل فجأة وفيه Request بتعمل Payment أو بتكتب في الـ Database، العملية ممكن تتقطع في نص الطريق وتسيب البيانات في حالة غير متسقة. باستخدام SIGTERM/SIGINT handlers، بنعطي السيرفر فرصة يخلص شغله الحالي الأول. ممكن يسأل Follow-upهل فيه وقت محدد ننتظره قبل ما نجبر الإغلاق؟ (في أنظمة كتير بيتحدد Timeout معين، ولو الـ Requests ما خلصتش خلاله، الـ Process بيتقفل إجباريًا عشان مايتعلقش للأبد).
