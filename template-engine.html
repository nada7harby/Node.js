📗 Chapter 1

Templating Engines Basics

قبل ما ندخل في أي Template Engine بالتفصيل، لازم نفهم أصلًا ليه فيه حاجة اسمها Template Engine، وإيه المشكلة اللي بتحلها.

1) يعني إيه Template Engine؟

🟣 إيه ده؟

Template Engine هي أداة بتخليكي تكتبي ملف HTML فيه أماكن فاضية (Placeholders)، وبعدين تملأها بـ Data حقيقية جاية من Server قبل ما ترسليها للـ Browser.

HTML Template + Data ↓ Template Engine ↓ HTML جاهز فيه القيم الحقيقية

2) ليه بنستخدمه؟

🟠 المشكلة

لو عايزة تعرضي صفحة بروفايل لكل User، مينفعش تكتبي HTML منفصل لكل واحد فيهم يدويًا. عايزة نفس الـ Structure، بس البيانات تتغير حسب اليوزر.

🔵 الحل

تكتبي Template واحد بس (زي profile.ejs)، وتخليه ياخد Data مختلفة في كل مرة، فيبني HTML مختلف حسب اليوزر من غير ما تكرري الكود.

3) Static HTML مقابل Dynamic HTML

Static HTMLDynamic HTML
محتوى ثابت، متكتب مرة واحدة يدويًامحتوى بيتبني وقت الـ Request حسب الـ Data
مفيش اتصال بـ Database أو Server Logicغالبًا جاي من Database أو منطق في الـ Server
نفس الملف لكل الزوارممكن يختلف من زائر للتاني

4) Server-Side Rendering (SSR)

SSR يعني إن الـ HTML بيتبني كامل جوه الـ Server الأول، وبعدين بيتبعت جاهز للـ Browser. الـ Browser مش محتاج يعمل حاجة زيادة عشان يبني الصفحة — هي وصلته HTML كامل خلاص.

🧠 Mental Model

فكري في Template Engine كأنها "خطاب جاهز فيه أماكن فاضية" (Dear ___، عندك ___ رسالة). الـ Server بيملأ الأماكن الفاضية دي بالبيانات الصح قبل ما يبعت الخطاب.

5) Template Engine Flow

Request ↓ Route ↓ Controller ↓ Data (من DB أو مباشرة) ↓ res.render() ↓ Template Engine ↓ HTML جاهز ↓ Response للـ Browser

❌ Common Mistakes

  • الخلط بين Template Engine ومكتبة Frontend زي React — Template Engine بتبني HTML جاهز على السيرفر، React بتبني الواجهة وتتفاعل معاها في المتصفح.
  • الظن إن Template Engine محتاجة Database إجباريًا — ممكن نمرر Data ثابتة أو جاية من أي مصدر، مش شرط Database.

Popular Template Engines

في عالم Node.js/Express، فيه كذا Template Engine مشهورة، وكل واحدة ليها Syntax وأسلوب مختلف.

1) EJS

EJS يعني Embedded JavaScript. أشهر وأبسط Template Engine مع Express، لأن Syntax بتاعتها قريبة جدًا من HTML عادي مع شوية JavaScript جواها.

example
<h1><%= name %></h1>

2) Pug

Pug (قديمًا Jade) بتستخدم Indentation بدل الـ Tags العادية، فالكود بيبقى أقصر، بس شكله مختلف تمامًا عن HTML العادي:

example
h1= name

3) Handlebars

Handlebars بتستخدم Syntax بالـ {{ }}، وبتفرض شوية قيود على كتابة JavaScript مباشرة جوه الـ Template (بتشجع فصل المنطق عن العرض أكتر):

example
<h1>{{name}}</h1>

5) إمتى نستخدم Template Engine وإمتى React/Next.js؟

⚡ خلي بالك

Template Engine مناسبة لمواقع بسيطة/متوسطة، Server-Rendered بالكامل، أو Admin Panels داخلية. React/Next.js أنسب لتطبيقات فيها تفاعل كبير من جانب المستخدم (Client-Side Interactivity) واحتياج لـ State معقدة في المتصفح.

  • اختيار Template Engine لمشروع محتاج تفاعل معقد من جانب المستخدم — في الحالة دي React/Next.js أنسب بكتير.

📗 Chapter 3

Express Setup with Template Engine

إزاي نجهز Express عشان يشتغل بـ Template Engine، ونعرف يلاقي ملفات الـ Views.

1) app.set("view engine", ...)

ده اللي بيقول لـ Express: استخدم الـ Template Engine ده:

example
const express = require('express');
const app = express();

app.set('view engine', 'ejs');

2) Views Folder

الافتراضي إن Express بتدور على ملفات الـ Templates جوه فولدر اسمه views/:

example
project/
│
├── views/
│   ├── profile.ejs
│   └── home.ejs
│
└── app.js

لو عايزة تغيّري مكان الفولدر:

example
app.set('views', path.join(__dirname, 'templates'));

3) res.render()

ده اللي بيقول لـ Express: ابني الـ Template ده وابعته كـ Response:

example
app.get('/profile', (req, res) => {
  res.render('profile');
});
res.render('profile') ↓ Express تدور على views/profile.ejs ↓ تبنيه HTML ↓ تبعته Response

4) إعداد EJS / Pug / Handlebars مع Express

🔹 EJS

example
npm install ejs
example
app.set('view engine', 'ejs');
// مفيش محتاجة require('ejs') يدويًا، Express بتكتشفها لوحدها

🔹 Pug

example
npm install pug
example
app.set('view engine', 'pug');

🔹 Handlebars

example
npm install express-handlebars
example
const { engine } = require('express-handlebars');

app.engine('handlebars', engine());
app.set('view engine', 'handlebars');

❌ Common Mistakes

  • نسيان app.set('view engine', ...) — Express مش هتعرف تفسر ملفات الـ Templates أصلًا.
  • وضع ملفات الـ Templates في مكان تاني غير views/ من غير ما نغيّر الإعداد — Express مش هتلاقيها وهترمي Error.

🎤 Interview Questions

إيه اللي بيحصل بالظبط لما تستخدمي res.render()؟
بيسأل عن إيه؟فهمك للخطوات اللي بتحصل بين استدعاء res.render() ووصول الـ Response للـ Browser. نفكر إزاي؟فكري: الملف اللي كتبتيه (.ejs مثلًا) مش HTML خالص، فمين اللي بيحوله؟ الإجابة المختصرةExpress بتدور على ملف الـ Template المطلوب جوه فولدر views، وتمرره للـ Template Engine المُعرّفة (زي EJS)، اللي بتاخد الملف والـ Data الممررة وتبني منهم HTML كامل، وبعدين Express بتبعت الـ HTML ده كـ Response للمتصفح. بالتفصيلالخطوة دي بتحصل كاملة على السيرفر قبل ما أي حاجة توصل للمتصفح؛ يعني المتصفح مش شايف ملف .ejs خالص، هو شايف بس HTML نهائي جاهز. ممكن يسأل Follow-upإيه اللي بيحصل لو الملف المطلوب مش موجود في views؟ (Express هترمي Error بتقول إن الـ Template مش موجودة، وده بيبقى غالبًا 500 Internal Server Error لو مفيش Error Handling مخصص).

📗 Chapter 4

Passing Data to Views

هنا بيتحدد الفرق الحقيقي بين HTML ثابت وHTML ديناميكي: إزاي نبعت Data من Express للـ Template نفسه.

1) إرسال Data من Express للـ Template

الـ Object التاني اللي بنمرره لـ res.render() هو اللي بيوصل للـ Template:

example
res.render("profile", {
  name: "Nada",
  age: 25
});

جوه profile.ejs، name وage بقوا متاحين مباشرة كـ Variables.

2) Variables

profile.ejs
<h1>اسمك: <%= name %></h1>
<p>عمرك: <%= age %></p>

3) Objects

ممكن كمان تبعتي Object كامل:

example
res.render("profile", {
  user: { name: "Nada", age: 25 }
});
profile.ejs
<h1><%= user.name %></h1>

4) Arrays

example
res.render("products", {
  products: [
    { name: "Laptop" },
    { name: "Phone" }
  ]
});

وهنشوف إزاي نعمل Loop عليها في فصل Loops & Rendering Lists.

5) Dynamic Content

🟠 الفكرة الأساسية

نفس ملف profile.ejs ممكن يعرض بيانات مختلفة تمامًا لكل مستخدم، لأن الـ Data اللي بتوصله من res.render() هي اللي بتتغير، مش الـ Template نفسه.

❌ Common Mistakes

  • محاولة استخدام Variable في الـ Template من غير ما تتبعت من res.render() — هيرمي Error زي "name is not defined".
  • نسيان إن أسماء الـ Keys في الـ Object لازم تتطابق مع الأسماء المستخدمة جوه الـ Template — أي اختلاف في الاسم يسبب undefined.

🎤 Interview Questions

إزاي بتوصل الـ Data من الـ Controller للـ Template بالظبط؟
بيسأل عن إيه؟فهمك للربط بين الـ Object اللي بتمرريه لـ res.render() والـ Variables المتاحة جوه الـ Template. نفكر إزاي؟فكري: لما تكتبي res.render('profile', { name: 'Nada' })، إزاي 'name' تبقى متاحة جوه profile.ejs؟ الإجابة المختصرةالـ Object اللي بتمرريه كـ Argument تاني لـ res.render() بيتحول لمتغيرات محلية متاحة مباشرة جوه ملف الـ Template، بنفس أسماء الـ Keys. بالتفصيللو الـ Object فيه { name: 'Nada', age: 25 }، الـ Template هيقدر يستخدم name وage مباشرة كـ Variables، من غير ما يحتاج أي Import أو تعريف إضافي. ممكن يسأل Follow-upإيه اللي بيحصل لو نسيتِ تبعتي Variable الـ Template محتاجاها؟ (هيرمي Error وقت الـ Render بيقول إن المتغير ده مش معرّف، وده بيوقف الـ Response كله لو مفيش Error Handling).

📗 Chapter 5

Template Syntax

هنركز هنا على EJS تحديدًا (الأشهر مع Express)، ونفهم الفرق بين أنواع الـ Tags المختلفة.

1) Output / Variables

example
<h1><%= name %></h1>

<%= %> بتطبع القيمة مباشرة جوه الـ HTML.

2) Expressions

مش لازم تكوني قيمة بسيطة، ممكن تكتبي Expression كامل:

example
<p>السنة الجاية: <%= year + 1 %></p>

3) JavaScript داخل Template

<% %> (من غير =) بتنفذ JavaScript عادي من غير ما تطبع حاجة — بتستخدم للـ Logic زي if وfor:

example
<% const total = price * quantity; %>
<p>الإجمالي: <%= total %></p>

4) Escaped Output

<%= %> بتعمل HTML Escaping تلقائيًا — يعني لو القيمة فيها Tags زي <script>، هتتحول لنص عادي مش هتتنفذ كـ HTML. ده الوضع الآمن الافتراضي.

5) Unescaped Output

<%- %> بتطبع القيمة كما هي من غير Escaping — يعني لو فيها HTML Tags حقيقية، هتتنفذ فعليًا كـ HTML:

example
<%- htmlContent %>
⚠️ خلي بالك

استخدمي <%- %> بس مع محتوى إنتِ واثقة إنه آمن (زي محتوى كتبتيه إنتِ)، وليس مع Input جاي من المستخدم مباشرة — هنرجع للنقطة دي بالتفصيل في فصل Security.

6) Comments

example
<%# ده تعليق مش هيظهر في الـ HTML النهائي %>

🆚 Don't Confuse These

Syntaxمعناها
<%= %>Output مع HTML Escaping (آمن، الافتراضي).
<%- %>Output من غير Escaping (خطير مع Input من المستخدم).
<% %>تنفيذ JavaScript logic من غير طباعة أي حاجة.
<%# %>Comment، مش بيظهر في الناتج النهائي.

❌ Common Mistakes

  • استخدام <%- %> مع بيانات جاية من المستخدم مباشرة — بيفتح باب لهجوم XSS، هنشرحه بالتفصيل في فصل Security.
  • الخلط بين <% %> و<%= %> — الأول بينفذ من غير طباعة، والتاني بيطبع القيمة.

🎤 Interview Questions

إيه الفرق بين <%= %> و<%- %> في EJS؟
بيسأل عن إيه؟فهمك للفرق الأمني بين Escaped وUnescaped Output. نفكر إزاي؟فكري: لو مستخدم كتب <script>alert('hi')</script> في Comment، إيه اللي المفروض يحصل لما نعرضه؟ الإجابة المختصرة<%= %> بتعمل HTML Escaping تلقائيًا (آمنة، الافتراضية). <%- %> بتطبع القيمة كما هي من غير أي Escaping، فلو القيمة فيها HTML/JavaScript حقيقي، هيتنفذ. بالتفصيللو استخدمنا <%= comment %> ومحتوى الـ comment فيه <script>، هيتحول لنص عادي معروض على الصفحة (آمن). لو استخدمنا <%- comment %> بنفس المحتوى، الـ script هينفذ فعليًا في متصفح أي زائر — وده باب لهجوم XSS. ممكن يسأل Follow-upإمتى يبقى استخدام <%- %> مقبول؟ (لما تكوني متأكدة إن المحتوى آمن ومش جاي من مستخدم مباشرة، زي HTML ثابت كتبتيه إنتِ نفسك أو جاي من مصدر موثوق تمامًا).

📗 Chapter 6

Conditional Rendering

إزاي نعرض جزء من الصفحة أو نخفيه حسب الـ Data اللي وصلت من الـ Server.

1) if / else

example
<% if (isLoggedIn) { %>
   <button>Logout</button>
<% } %>

ومع else:

example
<% if (isLoggedIn) { %>
   <button>Logout</button>
<% } else { %>
   <button>Login</button>
<% } %>

2) Conditional UI

ممكن نستخدمها لأي جزء من الواجهة بيتغير حسب الحالة، مش بس تسجيل الدخول — زي إظهار Badge "جديد" لو المنتج مضاف حديثًا، أو رسالة "مفيش نتائج" لو الـ Array فاضية.

3) إظهار عناصر حسب البيانات

example
<% if (products.length === 0) { %>
   <p>مفيش منتجات دلوقتي.</p>
<% } %>

4) Authentication-based UI

من أشهر استخدامات الـ Conditional Rendering: تغيير الواجهة حسب حالة تسجيل الدخول أو دور المستخدم (Role):

example
<% if (user && user.role === 'admin') { %>
   <a href="/admin">Admin Panel</a>
<% } %>

❌ Common Mistakes

  • نسيان قوس الإغلاق } جوه <% } %> — بيسبب Syntax Error في الـ Template بالكامل.
  • الافتراض إن user موجودة دايمًا من غير فحص (زي user.role مباشرة من غير user &&) — لو المستخدم مش مسجل دخول، user ممكن تكون undefined ويحصل Crash.

Loops & Rendering Lists

أكتر حاجة هتستخدميها فعليًا: عرض قائمة منتجات، يوزرز، أو أي بيانات جاية من الـ Database على شكل Array.

example

<% }) %>

لازم دايمًا نتأكد إن الـ Array مبعوتة من الـ Controller أصلًا قبل ما نعمل Loop عليها، وإلا هيحصل Error زي "Cannot read properties of undefined".

controller

  ]
});

controller

❌ Common Mistakes

  • عمل Loop على Array من غير ما تتأكدي إنها موجودة أصلًا — لو products undefined، الـ forEach هيرمي Error فورًا.

Forms with Templates

إزاي نبني Form جوه صفحة EJS، ونبعت بياناته لـ Express، ونعرض حالته (زي Errors) تاني.

1) HTML Forms

الـ Form في Template مبيختلفش عن أي HTML Form عادي — العنصر الأساسي بتاعها <form> بس بيدخل جوه ملف EJS زي أي عنصر تاني.

2) GET/POST Forms

الفورمات اللي بتضيف أو تعدل بيانات (زي إضافة منتج جديد) بتستخدم POST، والفورمات اللي بتبحث أو تفلتر (زي Search) غالبًا بتستخدم GET.

3) action و method

new-product.ejs
<form action="/products" method="POST">
  <input type="text" name="name" placeholder="اسم المنتج">
  <input type="number" name="price" placeholder="السعر">
  <button type="submit">إضافة</button>
</form>

action بيحدد الـ Route اللي هيستقبل الـ Form، وmethod بيحدد نوع الـ Request.

4) إرسال Form إلى Express

routes
app.post("/products", (req, res) => {
  const { name, price } = req.body;
  // هنا نضيف المنتج للـ Database مثلًا
  res.redirect("/products");
});
📝 ملاحظة

لازم يكون عندك app.use(express.urlencoded({ extended: true })) قبل الـ Routes عشان تقدري تقري قيم الـ Form من req.body.

5) عرض القيم داخل Form

لو عايزة تعرضي قيم قديمة (زي في صفحة Edit)، بتحطيها كـ Value للـ Input:

edit-product.ejs
<input type="text" name="name" value="<%= product.name %>">

6) Validation Errors

لو فيه غلط في البيانات، بنرجع نفس صفحة الـ Form تاني مع رسالة الخطأ:

routes
app.post("/products", (req, res) => {
  const { name, price } = req.body;
  if (!name) {
    return res.render("new-product", { error: "اسم المنتج مطلوب" });
  }
  res.redirect("/products");
});
new-product.ejs
<% if (typeof error !== 'undefined') { %>
   <p class="error"><%= error %></p>
<% } %>

❌ Common Mistakes

  • نسيان express.urlencoded() Middleware — req.body هيفضل Object فاضي مهما كتبتِ في الـ Form.
  • نسيان name للـ Input — من غير name، القيمة مش هتوصل خالص لـ req.body.
  • استخدام Variable في الـ Template (زي error) من غير فحص وجودها الأول — بيسبب Error لو الصفحة اتعرضت من غير error أصلًا.

🎤 Interview Questions

إزاي بتتعاملي مع Form بيبعت بيانات لـ Express وبيرجع رسالة خطأ لو فيه مشكلة؟
بيسأل عن إيه؟فهمك للدورة الكاملة: عرض Form، استقبال بياناته، والتحقق منها، ورجوع رسالة للمستخدم. نفكر إزاي؟فكري في المسار: المستخدم بيدوس Submit، الطلب بيروح فين، ولو فيه غلط، إزاي هيشوف رسالة الخطأ في نفس الصفحة؟ الإجابة المختصرةالـ Form بترسل بياناتها بـ POST لـ Route معين عبر action، الـ Route بيقرا البيانات من req.body، ولو فيه مشكلة (زي حقل فاضي)، بيعمل render لنفس صفحة الـ Form تاني مع تمرير رسالة الخطأ كـ Data. بالتفصيلالخطوة الأهم هي إن الـ Server بيرجع نفس صفحة الـ Form (مش صفحة تانية) مع الـ Error، عشان المستخدم يقدر يصلح غلطه من غير ما يضطر يكتب كل حاجة من الأول. ممكن يسأل Follow-upإيه الفرق بين res.redirect() وres.render() هنا؟ (render بيعرض صفحة مباشرة (زي رجوع لنفس الـ Form مع Error)، وredirect بيبعت المتصفح لـ Request جديد تمامًا لـ URL تاني، زي بعد نجاح الإضافة).

Security in Templates

أهم فصل في الجزء ده — إزاي نتجنب إن صفحاتنا تبقى باب لهجمات على المستخدمين.

1) HTML Escaping

الـ HTML Escaping معناه تحويل الرموز الخاصة (زي < و>) لنص عادي بدل ما تتفسر كـ HTML Tags حقيقية — وده اللي بيحمينا من إن أي Input خبيث يتحول لكود بيتنفذ فعليًا.

2) XSS (Cross-Site Scripting)

XSS هو هجوم بيحصل لما مستخدم خبيث يقدر يحقن كود JavaScript جوه صفحة بتتعرض لمستخدمين تانيين، وينفذ في متصفحهم — زي لو مستخدم كتب في Comment نص فيه <script> بيسرق الـ Cookies.

⚠️ خلي بالك

لو عرضتِ نص المستخدم ده بـ <%- comment %> (من غير Escaping)، الـ Script هينفذ فعليًا عند أي حد يفتح الصفحة.

3) Escaped vs Unescaped Output

زي ما اتشرح في فصل Template Syntax: <%= %> بتعمل Escaping تلقائي (آمنة، هي الافتراضية)، و<%- %> بتطبع كما هو من غير Escaping.

الحالةالاستخدام الآمن
Input جاي من مستخدم (Comment, Username, Search)<%= %> دايمًا
HTML ثابت كتبتيه إنتِ (زي نتيجة Partial include)<%- %> مقبول

4) عدم عرض User Input مباشرة بشكل غير آمن

❌ غلط

<%- userComment %> — لو userComment جاي من مستخدم مباشرة، ده باب مفتوح لـ XSS.

✅ صح

<%= userComment %> — الـ Escaping التلقائي بيحول أي كود خبيث لنص عادي مش هينفذ.

5) CSRF Basics مع Forms

CSRF (Cross-Site Request Forgery) هجوم مختلف عن XSS — بيحصل لما موقع خبيث يخلي متصفح المستخدم (وهو لسه Logged in عندك) يبعت Request لموقعك من غير علمه. الحماية الأساسية بتكون بإضافة CSRF Token مخفي جوه كل Form، والتحقق منه في الـ Server قبل قبول أي POST.

📝 ملاحظة

ده موضوع أعمق شوية بيتغطى غالبًا مع مكتبات الـ Authentication والـ Sessions، وهنا بنكتفي بمعرفة إنه موجود وإنه مختلف عن XSS.

❌ Common Mistakes

  • استخدام <%- %> مع أي بيانات جاية من مستخدم — أخطر غلطة أمنية في الـ Templates.
  • الافتراض إن كل بيانات الـ Database آمنة تلقائيًا — لو البيانات دي أصلها إدخال مستخدم (زي Comment)، لازم تتعامل معاها بنفس الحذر.

5) الـ Flow الكامل

Request ↓ Route ↓ Controller ↓ Model ↓ Database ↓ Controller ↓ View (EJS) ↓ HTML ↓ Browser
🧠 Mental Model

كل طبقة بتعرف بس اللي محتاجاه: الـ View معندهاش أي فكرة عن Database، والـ Model معندهاش أي فكرة عن HTML — والـ Controller هو الوسيط اللي بيربط بينهم.

❌ Common Mistakes

  • كتابة استعلامات Database مباشرة جوه ملف EJS — بيكسر فصل المسؤوليات، ويخلي الكود صعب الصيانة والاختبار.
  • حط Business Logic (زي حسابات معقدة) جوه الـ Template — المفروض ده يحصل في الـ Controller أو Model، والـ Template يعرض النتيجة الجاهزة بس.

SSR وres.send() مقابل res.render()

الفكرة الأساسية اللي عايزاكي تخرجي بيها من الفصل ده: الباك إند مش لازم يرجّع JSON بس. ممكن يرجّع HTML جاهز، وممكن يولّد HTML كـ String ويبعتها في Email، وممكن يستخدم Template واحدة ويحط فيها Data مختلفة كل مرة.

1) يعني إيه Server-Side Rendering (SSR) أصلًا

SSR معناها: السيرفر نفسه هو اللي بيجهز الـHTML قبل ما يبعتها للـBrowser.

تعالي نقارن. لو عندك صفحة Profile، في React SPA مثلًا ممكن يحصل:

Browser ↓ GET /api/profile ↓ Backend ↓ JSON ↓ React ↓ React تعمل HTML/UI

يعني Backend رجعت:

JSON response
{
  "name": "Nada",
  "email": "nada@example.com"
}

وبعدين React تعمل: <h1>{user.name}</h1>

لكن في SSR باستخدام Express + EJS:

Browser ↓ GET /profile ↓ Backend ↓ Database ↓ EJS Template ↓ HTML جاهز ↓ Browser

يعني Backend نفسها ترجع: <h1>Nada</h1><p>nada@example.com</p> — الـBrowser هنا مش محتاجة React عشان تركب الصفحة.

2) يعني إيه "الباك يولّد HTML"

عندك Template: <h1>Hello <%= name %></h1>، والBackend عندها name = "Nada". الـTemplate Engine بتعمل:

Template + Data ↓ Render ↓ HTML

وتطلع: <h1>Hello Nada</h1> — ده معنى Generate HTML.

الـFlow الكاملة لأي Request بيرجع صفحة من الباك:

Request ↓ Express Route ↓ Controller ↓ Get Data ↓ Template Engine ↓ Template + Data ↓ HTML ↓ Response ↓ Browser

3) res.send() مقابل res.render()

دي مهمة جدًا.

📝 res.send()

ابعت Response جاهزة زي ما هي. ممكن تكتبي res.send("Hello")، أو حتى تبعتي HTML كامل كـString، وده يرجع HTML — لكن إنتِ كتبتي الـHTML بنفسك جوه الكود، وده مش عملي لو الصفحة كبيرة.

res.send()
res.send("Hello");
// أو
res.send(`
  <html>
    <body>
      <h1>Hello Nada</h1>
    </body>
  </html>
`);

res.render() معناها: افتح Template، حط فيها Data، طلع HTML، وابعتها للـBrowser.

res.render()
res.render("profile", {
  name: "Nada"
});

لو عندك views/profile.ejs جواها <h1><%= name %></h1>، Express + EJS تطلع <h1>Nada</h1>.

Functionمعناها
res.send()إنتِ عندك Response جاهزة بالفعل.
res.render()إنتِ عندك Template + Data وعايزة تولّدي HTML.

4) إمتى أرجع JSON وإمتى HTML؟

اسألي: مين اللي هيستهلك الـResponse؟

لو React App: Frontend محتاجة Data → JSON (res.json(user)) لو Browser داخل صفحة Backend-rendered: Browser عايز صفحة → HTML (res.render(...))

مثال: GET /api/products ترجع [{"name": "iPhone"}]، لكن GET /products ممكن ترجع <h1>Products</h1><div>iPhone</div> — فممكن في نفس المشروع يبقى عندك الاتنين.

❌ Common Mistakes

  • كتابة HTML كامل جوه res.send() لصفحات حقيقية — مش عملي لو الصفحة فيها منطق أو حجم كبير، والصح هو res.render() مع Template منفصل.
  • الخلط بين الحالتين: مشروع REST API خالص وعايزة تضيفي صفحة HTML من غير سبب واضح — قرري الأول مين اللي هيستهلك الـResponse قبل ما تختاري JSON ولا HTML.

🎤 Interview Questions

بيسأل عن إيه؟فهمك للفرق العملي بين إرسال Response جاهزة وتوليد HTML من Template. نفكر إزاي؟فكري: لو عندك صفحة فيها 100 سطر HTML، هل معقول تكتبيها كلها جوه String في الكود؟ الإجابة المختصرةres.send() بتبعت Response جاهزة زي ما هي (نص، أو HTML مكتوب يدويًا). res.render() بتاخد اسم Template وData، تولّد HTML منهم، وتبعته كـResponse. بالتفصيلres.send() مناسبة لردود بسيطة أو مؤقتة، أما res.render() هي الأنسب لأي صفحة حقيقية فيها Structure وData متغيرة، لأنها بتفصل الـHTML (في ملف Template) عن الـLogic (في الـController). ممكن يسأل Follow-upهل ممكن نستخدم الاتنين في نفس المشروع؟ (أيوة، ممكن يبقى عندك res.json() لـAPI Routes، وres.render() لصفحات الـBrowser، في نفس الـExpress App).

Verification Pages

دلوقتي User وصلها Email فيها لينك تفعيل — نتابع إيه اللي بيحصل من لحظة الضغط على اللينك لحد تفعيل الحساب.

1) ضغط اللينك وقراءة الـToken

جوه الإيميل لينك زي https://example.com/verify-email?token=abc123. لما User تضغط عليه، الـBrowser تعمل GET /verify-email?token=abc123:

route + controller
router.get("/verify-email", verifyEmail);

async function verifyEmail(req, res, next) {
  try {
    const token = req.query.token;
    // verify token
  } catch (error) {
    next(error);
  }
}

لأن الـURL /verify-email?token=abc123، قيمة req.query.token بتساوي abc123.

2) التحقق من الـToken

يعتمد على تصميمك — غالبًا الـToken (أو نسخة Hash منه) مخزنة في الـDatabase مع الـUser:

User model
{
  email: "...",
  emailVerified: false,
  verificationToken: "...",
  verificationTokenExpiresAt: "..."
}
controller
const user = await User.findOne({
  verificationToken: hashedToken
});

وتتأكدي إنها مش Expired قبل ما تكملي.

3) لو Token صح ولو فشل

لو صح:

controller
user.emailVerified = true;
user.verificationToken = undefined;
user.verificationTokenExpiresAt = undefined;
await user.save();

res.render("verification-success");
verification-success.ejs
<!DOCTYPE html>
<html>
<body>
  <h1>Email Verified</h1>
  <p>Your email has been verified successfully.</p>
  <a href="/login">Login</a>
</body>
</html>

لو فشل:

controller
res.status(400).render("verification-failed", {
  message: "Verification link is invalid or expired."
});
verification-failed.ejs
<h1>Verification Failed</h1>
<p><%= message %></p>

4) الـFlow الكامل

Register ↓ Create User ↓ Generate Verification Token ↓ Store safe token representation + expiry ↓ Create Verification URL ↓ Render Email Template ↓ Send Email ↓ User clicks link ↓ GET /verify-email?token=... ↓ Backend reads token ↓ Validate token ↓ Find user ↓ Check expiry ↓ Mark emailVerified = true ↓ Invalidate token ↓ Render success page

5) نقطة أمان مهمة جدًا في الـTokens

⚠️ خلي بالك

متخليش Verification Token صالحة للأبد — اعملي Expiration (15 دقيقة، 30 دقيقة، ساعة، أو 24 ساعة حسب الـUse Case).

وكمان الأفضل تخزني Hash للـToken في الـDatabase بدل الـRaw Token نفسها:

Raw token → يتبعت للـUser فقط Hash(token) → يتخزن في DB

لما User يرجع الـToken، بنعمل Hash(receivedToken) ونقارنها باللي في الـDB. فلو الـDatabase اتسربت، الـTokens الخام مش موجودة أصلًا.

❌ Common Mistakes

  • خزّن الـToken الخام (Raw) في الـDatabase — لو الـDatabase اتسربت، أي حد يقدر يستخدم الـTokens دي مباشرة؛ الأفضل تخزين Hash فقط.
  • Verification Token من غير تاريخ انتهاء — لينك التفعيل يفضل شغال للأبد حتى لو المستخدم مسجلش أصلًا خلال دقائق.

Template Engine خارج res.render()

من أهم النقاط في الصفحة كلها: EJS نفسها Library تقدر تولّد HTML String من غير أي علاقة بـHTTP Response — دي اللي بتفتح الباب لاستخدامها في الإيميلات وPDF وأكتر.

1) EJS مش بس res.render()

ناس كتير تتخيل إن EJS معناها res.render() بس — لأ. EJS نفسها Library تقدر تولّد HTML String، بغض النظر عن استخدامها جوه Express Response ولا لأ.

2) res.render() مقابل ejs.renderFile()

res.render() بتستخدم لما عندك HTTP Response — Express بتلاقي الـTemplate، تعمل Render، وتبعت HTTP Response على طول:

Find Template ↓ Render ↓ Send HTTP Response

ejs.renderFile() مختلفة — بترجعلك HTML String بس، مش بتبعتها لأي حد، وإنتِ تقرري تعملي بيها إيه:

example
const html = await ejs.renderFile(templatePath, data);
🧠 احفظي الفرق ده

res.render() = Render Template + Send HTTP Response. أما ejs.renderFile() = Render Template + Return HTML String.

3) استخدامات ejs.renderFile()

الـHTML String الناتج ممكن يروح لأي حتة — مش بس Browser:

ejs.renderFile() ↓ HTML String ├─ Email (Nodemailer) ├─ PDF (HTML-to-PDF tool) ├─ HTML response يدوي (res.send(html)) └─ أي استخدام تاني

مثال Email (زي ما شفنا في فصل Email Templates):

example
const html = await ejs.renderFile(templatePath, { name, verifyUrl });

await transporter.sendMail({ to: email, subject: "Verify your email", html });

مثال HTML Response يدوي:

example
const html = await ejs.renderFile(templatePath, data);
res.send(html);

ده شبه res.render(...)، لكن إنتِ عملتي الـRender بنفسك.

مثال PDF (زي Invoice):

invoice.ejs
<h1>Invoice #<%= invoice.id %></h1>
<p>Total: <%= invoice.total %></p>
Render HTML ↓ Generate PDF ↓ Download / Email

وحتى ممكن نستخدم Template System لرسائل Notification (مش لازم HTML حتى، حسب الـEngine والـUse Case) — زي "Hello {{name}}, your order {{orderId}} is ready."

4) تنظيم الكود: Email Service منفصل

بدل Controller فيها كل حاجة (Generate Token, Build URL, Render Template, Create Transport, Send Mail)، نظمي الملفات:

const path = require("path");

async function sendVerificationEmail({ user, token }) {
  const verifyUrl = `${process.env.APP_URL}/verify-email?token=${token}`;

  const templatePath = path.join(__dirname, "../emails/verify.ejs");

5) أهم طريقة تفكير عايزاكي تمشي بيها

أي Template تقابلك اسألي نفسك الأسئلة دي بالترتيب:

1) الـHTML دي هتروح فين؟ (Browser → res.render() | Email → ejs.renderFile() | PDF → renderFile() ثم PDF generator) 2) الـData جاية منين؟ (Database, Request, Config, Generated Token, URL) 3) هل الـData دي Trusted؟ (لو User Input: Escape, Validate, Sanitize لو HTML مسموح) 4) هل فيه Secret أو Token؟ (لو آه: Expiry, One-time use, متعمليش Log, HTTPS, إلغاء بعد الاستخدام) 5) هل الـTemplate فيها أجزاء متكررة؟ (لو آه: Partials)
🟠 الفكرة الأساسية

الموضوع مش مجرد EJS Syntax — ده بقى Flow شغل كاملة، وده الفرق بين حد بيحفظ Syntax وحد فاهم إزاي يبني Feature حقيقية.

6) الخريطة النهائية

TEMPLATE ENGINE ├─ Web Pages → res.render() → HTML Response → Browser └─ Emails → ejs.renderFile() → HTML String → Nodemailer → Email

ومعاهم دايمًا: Variables، Conditions، Loops، Partials، Escaping، Dynamic Data. وفي Auth Flows بالتحديد: Verification، Reset Password، OTP.

❌ Common Mistakes

  • الاعتقاد إن EJS مربوطة بـres.render() فقط — ده بيمنعك من استخدامها في سيناريوهات قوية زي الإيميلات وPDF.
  • حط كل منطق الإيميل (Token, URL, Render, Send) جوه الـController مباشرة — بيصعب القراءة والاختبار؛ الأفضل Service منفصل.
